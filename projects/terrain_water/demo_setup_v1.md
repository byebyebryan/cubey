# Terrain Water: explicit demo setup

The live terrain-rain demo is an active Cubey application with optional external
inputs, not a fresh-checkout-only example. Setup is deliberately separate from
normal build/startup. Nothing below is run automatically by CMake or the launcher.
For runtime defaults and capabilities, see the [current reference](current_reference.md).

For upstream credit, the hash-locked Python environment, explicit source build,
import checks and new-build qualification gates, use the
[SynxFlow dependency handoff](../fluid/fluid_25d/external_synxflow/README.md). The stock PyPI package
supplies IO tooling; it is not a replacement for the controlled service extension.

## What must exist

| Input | Responsibility / check |
| --- | --- |
| Vulkan renderer | Normal Release build; video capture additionally needs Cubey's libav/FFmpeg support. |
| Terrain elevation and climate | Shared Terrain source cache; source hashes and world-coordinate crop are validated. |
| Prepared native case | Explicit serializer output under a caller-owned study directory; immutable input hashes and native bed identity. |
| Worker Python environment | Linux x86_64 / CPython 3.11, glibc >= 2.28; [hash-locked dependencies](../fluid/fluid_25d/external_synxflow/requirements-linux-cp311.lock). Keep the venv interpreter path, not its resolved symlink target. |
| Service extension | Existing audited SynxFlow service build; SHA-256 must match the qualified artifact. A different build is not admitted merely by supplying a path. |
| GPU runtime | Compatible NVIDIA CUDA runtime for the external worker, plus Vulkan support for Cubey. These are separate APIs/processes, not Vulkan-CUDA shared-buffer interop. |

Replay uses saved fields and does not need the worker/CUDA extension. The builtin
diagnostic scenario needs neither the external terrain nor SynxFlow.

## Terrain prerequisite

The dedicated renderer target is `cubey_project_terrain_water`; the managed
launcher selects `build/release/projects/terrain_water/terrain_water`. The builtin
Fluid 2.5D target remains independent. Legacy preparation helpers and qualified
native artifact paths are deliberately retained, not relocated or requalified.

The curated [site catalogue](../fluid/fluid_25d/terrain_water_sites.json) pins existing shared
Terrain sources, not assets generated by the Fluid application. For the default
Mountain site it requires the temperate-mountain-valley source under
`cache/terrain/sources/v1/landscape-variations/`, including its climate companion.
The default patch samples a fixed physical crop at 1024² / 16 m from 30 m elevation.

See [Terrain's explicit preparation workflow](../terrain/README.md#world-first-prepared-sites-opt-in)
and its [landscape tooling](../terrain/tools/terrain_diffusion_bake.py).
Use the retained matching terrain package or explicitly regenerate/restore its
source before preparing cases. Missing or different sources are an error, not a
reason to normalize a new terrain into the old identity. Fresh generation across
other hardware is not promised to reproduce the same bytes.

## Prepare one case, not an entire survey

With the existing IO environment and matching terrain cache, replace the Python
placeholder below with that environment's interpreter. The output case must be
fresh; this operation serializes inputs and does not run a hydraulic simulation.

```sh
rtk proxy mkdir -p outputs/fluid/demo-local/cases
rtk proxy /path/to/worker-env/bin/python -B \
  projects/fluid/fluid_25d/prepare_live_perf_terrain_v1.py \
  --site mountain --configuration patch-1024-16m --rain 512 \
  --out outputs/fluid/demo-local/cases/mountain-patch-1024-16m
```

Other curated cases can be prepared explicitly in the same `cases` directory.
The launcher shows missing cases as disabled; it does not require a 30-case batch
to display the one prepared Mountain case. Apply/restart always creates new dry
water rather than transferring state across terrains or resolutions.

## External runtime is opt-in and currently qualified by artifact

The service build helper and worker are a separately marked GPL-3.0-only slice in
`external_synxflow/`. They are not linked into the Vulkan renderer and are not
built by normal Cubey targets. Current reference pins are declared in
[the service build helper](../fluid/fluid_25d/external_synxflow/build_synxflow_service_v1.py) and
[the launcher runtime profile](../fluid/fluid_25d/run_mountain_rain_demo.py).

To inspect the explicit build inputs without building or installing anything:

```sh
rtk proxy python3 projects/fluid/fluid_25d/external_synxflow/build_synxflow_service_v1.py --help
```

The helper accepts a SHA-pinned upstream archive, explicit private CUDA toolkit,
CPython and C/C++ compilers, then builds into a fresh private directory. See the
[retained source-build and parity evidence](../fluid/fluid_25d/README_HISTORY.md#optional-gpl-external-service-worker)
before attempting a new build. Toolkit/compiler/extension setup is **not** a
portable one-command installation or an accepted arbitrary-build profile today.
Normal demo startup does not install packages, models or toolchains.
The [dependency walkthrough](../fluid/fluid_25d/external_synxflow/README.md#2-restore-a-qualified-service-or-build-a-candidate)
contains the full explicit build command; `--help` alone is not setup.

`run_terrain_rain_demo.py` now accepts `--native-python` and `--extension` so the
same qualified artifacts need not be located at a maintainer's dated paths.
These overrides retain the exact hash guard. The older defaults remain a local
convenience, not a general deployment claim. A different native binary requires
a separate correspondence/parity and lifecycle qualification pass.

## Preflight and bounded headless check

Replace the two runtime paths with existing qualified artifacts:

```sh
rtk proxy python3 projects/terrain_water/run_terrain_rain_demo.py \
  --study outputs/fluid/demo-local \
  --native-python /path/to/worker-env/bin/python \
  --extension /path/to/qualified/flood.cpython-311-x86_64-linux-gnu.so \
  --print-command
```

This checks the selected case/source/artifact identities and prints the worker
and viewer commands without starting either. It does not prove all runtime
dependencies are usable; the actual worker handshake is a separate runtime check.

Optionally add `--check-runtime` alongside live `--print-command` to verify host
ABI, locked packages and the qualified native/IO imports. Library caches are
temporary; no CUDA solver is dispatched. This option is rejected for replay or
ordinary launches, and does not install dependencies or admit another build.

Add `--headless --run-seconds 20 --out outputs/fluid/demo-smoke-FRESH` for a
bounded offscreen check instead of `--print-command`. With no regression script
the worker stays dry and paused. The launcher clears display-server variables,
uses real Vulkan offscreen rendering, and closes only its owned processes.
Check `launch.json`, `worker.log`, `viewer.log` and the cleanup receipts. No X11,
Xvfb, GUI interaction or native presented-FPS claim is implied.

## Data and media provenance

The featured terrain is generated, not a surveyed location. Its manifest pins
Terrain Diffusion code/model revisions and native source hashes. The local source
checkout and pinned model card declare MIT; the service slice declares GPL-3.0-only.
The media manifest records those declarations and source identities separately
from Cubey's MIT renderer. Native depth/momentum archives remain ignored inputs,
not code/media payloads silently added to the repository.

Presentation videos render real recorded states. Rain, foam and dots/trails are
render-only cues, not conserved native particles. Timelapse rates and held-state
cadence belong in provenance; encoded 60 FPS does not certify solver or scanout FPS.
